# Gambit skill conventions

The repo-specific rules. Everything not listed here is ordinary skill authoring — trust your
judgment and the live upstream docs.

## Deliberate deviations from upstream

**The `description` states WHEN, not WHAT.** Upstream tells you to include both what the skill does
and when to use it. Gambit does not, and this is measured, not stylistic: a description reading
"review code between tasks" caused Claude to perform ONE review when the skill body required TWO.
The description is read at routing time and its content leaks into execution. Write triggers,
symptoms, and contexts — plus what the skill is *not* for, because the nearest wrong match is what
actually causes misrouting.

**No `@` links in skill bodies.** They load eagerly, which defeats the point of a reference file.
Refer to `references/<file>.md` by name and let the model open it when it gets there.

**No worked examples where a schema will do.** An output contract (the fields a downstream skill
parses) belongs in the skill. A transcript demonstrating a rule already stated in prose does not —
it narrows the model to the example's shape and costs tokens on every invocation.

## Mechanics

- **`src/` is canonical.** `skills/`, `codex-contracts/`, and `plugins/gambit/` are generated by
  `tools/render_skills.py`. Edit `src/`, then `just generate`, then `just check`.
- **Backend blocks.** Paired HTML-comment markers fence genuinely divergent per-backend semantics;
  copy the exact syntax from any existing SKILL.md. (Don't write the marker tokens in prose — the
  renderer matches them anywhere in a line, including inside backticks, and an unpaired mention
  fails the build.) Do not fork a whole passage for vocabulary alone — the renderer's
  `CODEX_REPLACEMENTS` already substitutes nouns like task/worker-brief.
- **The renderer and tests pin exact phrasings.** `tools/render_skills.py` matches specific source
  strings, and `tests/` asserts on substrings from skill prose. Rewording can silently change Codex
  output or fail a test guarding real behavior. Read the assertion before changing either side.
- **Never write a concrete model ID.** Dispatch at a tier alias resolved through
  `codex-contracts/models.md`.
- **The dispatch tool is `Agent`.** A bare `Agent` line opening a fenced block is rewritten to
  `SpawnAgent` for Codex. Do not confuse it with `SessionPlanWrite`/`SessionPlanWrite`, which are task-tracking
  tools and stay as-is.
- **Contracts live in `src/codex-contracts/` and are passed by path**, never read into the dispatcher's
  own context. `src/codex-contracts/README.md` owns the class and role enum.

## Sizing

Keep a SKILL.md under ~500 lines. Past that, split into `references/` files that each gate their
own applicability ("Use when… / Don't use when…") and route to them from the decision point where
they apply — see `skills/debugging/` for the shape worth copying: a short body, a symptom→file
dispatch table, and reference files loaded only when their situation arises.

## Validating a skill change

A skill that enforces a discipline under pressure needs a pressure test before shipping: dispatch a
subagent at the cheap tier with a realistic scenario that tempts the shortcut, and check behavior,
not recitation. Ask "what do you do?", never "what should you do?" — and don't tell the test agent
the loophole you're probing. Record the result in `src/codex-contracts/VALIDATION.md`.

Mechanical edits — a typo, a path fix, a reworded heading — do not need a pressure test.
